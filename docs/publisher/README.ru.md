# Собери своего публикатора

[English](README.md) · [Рецепт для агента](../../recipes/publishing/publishing-build-your-publisher.md)

Это задание агенту по устройству нашей отдельной видеомастерской. **Здесь рецепт, а не установленный публикатор:**
в репозитории нет CLI загрузки и готовых адаптеров площадок. Новый рецепт остаётся гипотезой, пока по нему
не собрали свой публикатор и не записали результат проверки на настоящем аккаунте.

Рендерер отдаёт MP4. Публикатор принимает именно этот файл, готовит загрузки и записывает, что произошло.
Так можно поправить подпись или продолжить с одной площадкой, не рендеря и не публикуя всё заново.

## Минимальная полезная версия

Отдельный проект на Node.js/TypeScript, Playwright и постоянная очередь. Сначала одна площадка и один аккаунт.
YouTube, TikTok и Instagram — разные адаптеры, работоспособность каждого проверяется отдельно. Можно выбрать другой стек.

| Часть | За что отвечает |
|---|---|
| Планировщик | Проверяет существующий MP4, считает SHA256, готовит метаданные и показывает точные цели |
| Хранилище очереди | Атомарная запись и один владелец задания; сохранение состояния при падении |
| Менеджер профилей | Отдельный локальный профиль на площадку/аккаунт, ручной вход, блокировка занятого профиля |
| Адаптер | Проверяет аккаунт, загружает/отправляет, возвращает ID, находит существующий черновик или пост |
| Сверка результата | Разбирает неопределённую попытку по данным площадки; таймаут не запускает повторную загрузку |
| Реестр | Хеш файла, аккаунт, хеш метаданных, история попыток, ID/URL, видимость и доказательство проверки |

Ключ задания: **хеш файла + площадка + аккаунт**. В записи также путь к файлу, заголовок, подпись, требуемая
видимость, хеш метаданных, состояние и попытки. Разрешение привязано к точному файлу, метаданным, аккаунту
и видимости. Изменилось любое поле — нужно новое разрешение. Одного пути к MP4 недостаточно.

Состояния площадок независимы: успешная загрузка на YouTube не теряется из-за сбоя TikTok.

## Состояния и восстановление

Возможные состояния: `ready`, `uploading`, `draft`, `processing`, `published`, `needs_review`, `failed`.

- До внешнего действия записать `uploading` и номер попытки. Полученный ID сразу сохранить, до следующих действий в UI.
- Падение, таймаут или отсутствие подтверждения после отправки означает **`needs_review`**. Это относится и к
  найденному после перезапуска `uploading`.
- Сначала проверить существующие черновики/посты. Есть ID — проще; отсутствие сохранённого ID не доказывает,
  что загрузки не было. Данных недостаточно — остановиться для проверки человеком. Клики браузера не гарантируют
  «строго одну отправку».
- Найденный черновик остаётся `draft`, отправленное на модерацию — `processing`. Это ещё не публичный ролик.
- `published` ставится после проверки аккаунта, сохранённого ID/URL, требуемой видимости и метаданных. Записать,
  как проверяли: страница Studio под своим аккаунтом не доказывает доступность ролика без входа.
- Достоверный сбой до отправки можно повторить после устранения причины. Неопределённую отправку автоматически не повторять.

Настоящую отправку запускает человек после просмотра точного задания. Скилл собирает и проверяет публикатор,
но не входит в аккаунты, не отправляет видео и не меняет [правила публикации тулкита](../../AGENTS.md).

## Браузер и контракт адаптера

Профиль для автоматизации отдельный, повседневный профиль браузера не использовать. Вход и MFA выполняет человек.
При входе и загрузке использовать один браузер/канал. Профили, cookies, трассировки и скриншоты с данными аккаунта
не класть в Git. Первоисточники: Playwright про [постоянный контекст](https://playwright.dev/docs/api/class-browsertype#browser-type-launch-persistent-context)
и [сохранённую авторизацию](https://playwright.dev/docs/auth).

Адаптер реализует следующие операции. Это **интерфейсы для реализации**, готовых функций в тулките нет:

| Операция | Наблюдаемый результат |
|---|---|
| `preflight` | Аккаунт совпал, сессия действует, нужные элементы доступны; отправки не было |
| `upload` | Файл передан целиком, сохранён ID черновика/отправки и состояние либо явно указана неопределённость |
| `inspect` | Существующий ID/черновик/пост, аккаунт, видимость, метаданные и состояние обработки |
| `verify` | Доказательство нужного результата, настройки аудитории/комментариев, когда применимо |

У адаптера записать проверенные браузер, ОС, язык интерфейса, дату и использованную документацию площадки.
Перед настоящей проверкой изучить текущие способы загрузки и условия. Одна удачная попытка не доказывает вечную
поддержку. Проверка входа или изменившийся UI — повод остановиться, а не добавлять обходы, решение CAPTCHA или копирование сессий.

## Задание агенту

```text
Собери отдельный личный публикатор по docs/publisher/README.ru.md в клоне not-a-blogger.
Используй Node.js/TypeScript и Playwright, если у целевого проекта ещё нет подходящего стека.
Спроси только недостающие площадки/псевдонимы аккаунтов и место нового проекта.
Сначала реализуй планирование, постоянную очередь по целям, блокировки профилей, фейковый адаптер и тесты восстановления.
В новом проекте сделай CLI plan/dry-run, login, run, inspect, reconcile и покажи настоящий вывод справки.
Dry-run работает без сети и браузера, очередь не меняет. Login выполняю вручную я.
Разрешение привяжи к SHA256 файла, метаданным, аккаунту, площадке и видимости. Устаревшее разрешение отклоняй.
Таймаут/падение при отправке означает needs_review и проверку до повтора; слепых повторов нет.
Настоящие адаптеры добавляй по одному. Нереализованные площадки недоступны; фейковый адаптер не считается настоящим.
Отдай результаты тестов, точные команды для моей проверки на аккаунте и оставшиеся ограничения.
При сборке не обращайся к аккаунтам, не входи в них, не загружай и не публикуй видео, не копируй существующие сессии.
```

## Проверки перед передачей

Эти случаи сначала воспроизвести с фейковым сервисом или локальными фикстурами:

1. Dry-run не обращается к сети/браузеру и побайтно сохраняет очередь.
2. Изменённый MP4, подпись, аккаунт или видимость отменяют разрешение до внешнего действия.
3. Два процесса не могут владеть одним заданием/профилем; старый процесс не перезаписывает новый результат.
4. Падение после условно успешной отправки даёт `needs_review`; сверка находит существующий ролик без второй отправки.
5. Сохранённый `uploading` без ID остаётся неопределённым до проверки; точно найденный черновик используется повторно.
6. Готовая площадка пропускается, другая восстанавливается; `processing` не называется `published`.
7. Битая очередь, другой аккаунт, истёкший вход, неподдерживаемый адаптер и изменённый UI дают понятную ошибку без отправки.

Так проверяется локальная логика. Человек отдельно испытывает точный одобренный файл на нужном аккаунте и записывает
ID/URL, видимость, результат и дату. До этого статус адаптера — **не проверен на настоящем аккаунте**.

Человеку для проверки пригодятся [рецепты публикации](../../recipes/publishing/README.md): завершение загрузки,
поиск черновика, настройки аудитории. Утилиты подготовки: [кредиты](../../tools/README.md) и
[паспорт результата](../../starter/DELIVERY.md).
